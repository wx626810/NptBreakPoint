# NpHv 伪附加方案进度报告与转向说明（2026-08-28）

## 1. 结论先行

伪附加（LSTAR 拦截 DAP/Wait/Continue + 自建 DEBUG_EVENT 队列）这条路线，
驱动侧已经走到“断点命中 → 事件入队 → 标准字节投递成功”，但卡在目标
x64dbg（2026-05-27 构建）对伪异常事件“既不暂停也不 Continue”，且与该
版本官方源码行为对不上。经排查，高度怀疑 VM 上的 x64dbg 二进制与官方源码
不一致（或存在未公开的改动）。因此按用户决定：暂停伪附加方案，转向
“让调试器真实附加，再抹掉所有调试特征（含 DebugPort）”。

## 2. 伪附加方案已完成的工作

### 2.1 SSDT 定位（已完成，闭环验证）
- 不再全镜像扫描，读取 KeServiceDescriptorTable，用 TableBase + 结构校验
  选表；表项解码 entry >> 4，地址 = TableBase + (entry >> 4)。
- windbg 实测：KeServiceDescriptorTable、TableBase、489 个服务、4B 表项
  08d13601 全部对得上。
- 用于解析 NtDebugActiveProcess(214)、NtWaitForDebugEvent(484)、
  NtDebugContinue(215) 等 12 个基础拦截项 + 动态 QSI(54)。

### 2.2 LSTAR 跳板（已打通）
- 跳板逐 syscall 比对，命中走 vmmcall + Guest 内核分发器；
- 透传路径恢复现场重新进入原始 KiSystemCall64（不调用真实 Nt*），
  修复 Explorer/svchost 崩溃；
- trampoline slots / chain / miss / hit 已实测。

### 2.3 事件投递链路（已打通到 x64dbg Wait）
- 伪会话：NpPseudoDbgCreateSession / Wait / Continue / Detach；
- 快照：CREATE_PROCESS + CREATE_THREAD + LOAD_DLL（现已跳过）+ 初始断点；
- 多会话修复：断点事件入队到目标全部活动会话（否则旧会话抢事件）；
- DEBUG_EVENT 写入 0xB0，dwFirstChance 写 0xA8，不越界；
- wait delivered status=0 已确认事件成功拷入 x64dbg 缓冲。

### 2.4 稳定性修复（多个蓝屏根因已修）
- 物理直读：5 级页表（LA57）支持 + 附加虚拟读兜底；
- MmCopyVirtualMemory 改 KernelMode 后补 ProbeForRead/ProbeForWrite，
  修复 0x50（坏用户指针直接写崩）；
- 进程退出锁页：断点记录 OwnerProcess，轮询线程自动解锁 MDL，
  修复 0x76（PROCESS_HAS_LOCKED_PAGES）；
- 看门狗对 HALT 断点页 #NPF 豁免，防误判 0xDEAD0001。

### 2.5 NPT 断点（已能命中）
- 模式 1（当前默认）：取指整页切 CC 副本页，保证命中；
- 模式 0：干净页 + TF 单步逼近（保隐蔽，syscall 清 TF 可能漏）；
- 命中日志：#BP hit → bp queued 已验证。

## 3. 当前阻塞点

#BP hit 与 bp queued 均出现，事件以标准字节
（p10=0x80000003 p20=断点地址 pA8=1）投递成功，但 x64dbg 的 DebugLoop
（同一线程 tid）消费事件后既不暂停也不调用 ContinueDebugEvent，继续轮询
Wait。官方 2026-05-27 源码 + TitanEngine 源码均确认“所有事件分支最终必然
Continue”，与实测行为矛盾。

推断：
1. VM 上的 x64dbg/TitanEngine 二进制疑似与官方源码不一致；
2. 或伪事件仍缺少某个 x64dbg 运行时依赖的字段/状态。

## 4. 转向方案：真实附加 + 抹特征

让 NtDebugActiveProcess 真实建立 DebugPort，x64dbg 走真实调试事件；
同时把目标/调试器身上的所有调试痕迹抹掉：

- DebugPort / ProcessDebugPort → 0；
- ProcessDebugObjectHandle → STATUS_PORT_NOT_SET；
- ProcessDebugFlags → 1（允许调试）；
- PEB BeingDebugged、NtGlobalFlag → 干净；
- 调试器进程/线程从枚举中隐藏（QSI）；
- 断点恢复真实 0xCC 落内存（或保留 NPT 无痕模式供其它用途）。

待办：
- NpLstar：DAP/Wait/Continue 改为透传真实路径（或按模式开关）；
- NpDebugHide：加强 QIP/PEB 抹除、DebugPort 清空、句柄隐藏；
- 验证 x64dbg 真实附加后断点/暂停/单步全链路；
- 与 NPT 无痕断点并存时的切换策略。
## 5. 转向后的细化：真实 DebugPort + NPT 无痕断点（混合方案）

用户提出：能否用 NPT 同时藏 DebugPort 和代码页 0xCC？

结论：
- 0xCC：可以。NPT 双影子页让“读视图干净、执行视图 CC”，0xCC 不落内存。
  命中时 NPT 影子页执行 INT3 → 真实 #BP 异常 → 由真实 DebugPort 投递真实
  EXCEPTION_BREAKPOINT 给 x64dbg。x64dbg 拿真实事件（兼容），内存无 CC（隐蔽）。
- DebugPort：不能靠 NPT 藏。DebugPort 是 EPROCESS 内核字段，与全系统共享
  同一物理页；NPT 按 CPU 映射，无法只对目标进程把该字段读成 0。用户态查询
  已由 QIP 分流隐藏；内核态直接读 EPROCESS 需要另做定向拦截。

当前实现（02:12 之后）：
- DAP：保护目标 + 登记调试器 + 透传真实 NtDebugActiveProcess（真实 DebugPort）；
- Wait/Continue：无伪会话透传真实路径；
- 0xCC 写入：恢复 NPT 断点（不落内存），DEBUGGER 模式无伪会话时向 Guest
  注入 #BP → 真实 DebugPort 投递；
- QIP/PEB/prochide 抹特征保留。

复测预期：
- 日志出现 [dbg] real attach ... (passthrough)；
- F2 下断点仍显示 [dbghide] 0xCC write -> NPT breakpoint（CC 不落内存）；
- 命中后 x64dbg 应收到真实异常并暂停。
## 6. 窗口期分析（真实附加 + NPT 混合方案）

- DebugPort：非窗口期，是持续存在。用户态查询从附加瞬间起被 QIP 隐藏
  （保护在真实 DAP 透传前生效）；内核级直读 EPROCESS 始终可见。
- 0xCC：基本无窗口。0xCC 不落内存，读视图始终干净；仅 NPT 安装失败
  回退真实写时才会暴露。
- PEB BeingDebugged/NtGlobalFlag：原先有窗口（内核置位 → 节流清扫之间）。
  已新增 1ms 定时 PEB 清扫线程（NpDebugHideSweepThread），把直读 PEB 的
  检测窗口压缩到毫秒级。IsDebuggerPresent 是纯用户态直读，无法用 QIP
  拦截，只能靠高频清扫覆盖。
## 7. PEB 抹除策略调整（2026-08-28 02:26）

- 1ms 高频轮询副作用明显（CPU 开销、周期性写 PEB 可被硬件写断点/页属性
  检测、与目标堆标志可能冲突）。
- 已改为 100ms 低频安全网 + 查询/命中即时抹除。BeingDebugged/NtGlobalFlag
  只在附加瞬间由内核置位一次，不是持续变化，100ms 安全网足够覆盖边界。
- 附加瞬间的窗口（内核置位 → 下一次清扫）若要压到近零且无写入痕迹，
  正解是 NPT PEB 影子页：真实页置写保护，写操作单步同步到影子页，
  影子页恒返回干净字段，真实 PEB 永不被写。列为下一阶段待实现。
## 8. PEB 影子页 NPT 实现（2026-08-28）

目标：不再周期写真实 PEB，改为 NPT 影子页。真实 PEB 页置写陷阱，
Guest/调试器/物理直读看到的一律是干净副本（BeingDebugged=0、
NtGlobalFlag 清 heap 标志），真实页只在写陷阱释放窗口内被 OS 短暂写入。

改动：
- MONITOR_INFO 增加 IsPebShadow/OwnerProcess/ShadowPage/ShadowPagePA/
  UserPageMdl/UserPageSystemVa；
- NpSetMonitorLeaf：PEB 影子收紧=影子页(W=0,NX=1)，放行=真实页(W=1,NX=1)；
- #DB 监视分支：先 NpMonSyncPebShadow 同步影子再重新收紧；
- 新增 NpBreakPointInstallPebShadow：AttachProcess → MDL pin 真实 PEB 页 →
  分配影子页 → 复制并清字段 → 全 CPU 部署；失败/卸载路径由
  NpMonFinalRelease 统一回收 MDL/影子页/进程引用；
- NpBreakPointUninstallByProcess 现在同时摘除 PEB 影子监视（进程退出联动），
  500ms 清扫线程兜底；新增 NpBreakPointUninstallPebShadowByPid（解保护时用）；
- NpMemAccessRead：命中 PEB 影子时物理直读改读影子页 PA（RPM 也返回干净值）；
- NpDebugHide DAP 真实附加成功后自动安装 PEB 影子；NpDbgHideSweepThread
  检测到影子在位时跳过真实页写入（安全网保留，影子在位时零周期写）。

产物：output\NpHv.sys（Release）、output\NpHv-Debug.sys（Debug），
Debug/Release 均构建通过。

剩余风险：
- 外部驱动绕过本驱动直接读真实 PEB 物理帧仍可见真实字节（NPT 只作用于
  Guest 虚拟访问）；如需彻底物理隐藏，需配合真实页保持干净或拦截外部读。
- 写陷阱释放窗口仅一条指令（TF 单步），仅限触发 CPU 的 ASID，其它 CPU
  始终看影子。

## 9. 断点窗口期修复（2026-08-28）

### CC 窗口成因
断点取指策略 NP_BP_PAGE_CC_ON_IFETCH=1：只要进入断点页，当前核的 NPT
叶子就整页切到 CC 副本（断点偏移处为 INT3）。若取指不在断点偏移（近距
取指），不会触发 #BP，叶子会停在 CC 副本，直到复位线程重新武装；debug-
hide 活跃时复位周期 1ms，因此同核自读该页最坏有约 1ms 能看到 0xCC。
真实物理页从不含 CC，物理读/DMA/其它核均不可见。

### 安装部署间隙（记录，不做处理）
安装断点时先 pin 页、拷影子，再逐核部署 NX=1；未部署到的那颗核上执行
到断点地址会直接跑过一次原指令。微秒级，无 CC、不落内存，仅漏一次命中。
要压到近零需安装前冻结目标全部线程，侵入性大，本次不做。

### 功能窗口修复：DebuggerPaused 暂停线程特判
- BREAKPOINT_INFO 增加 DebuggerPausedThreads[8] / DebuggerPausedCount；
- #BP 命中（真实附加 DEBUGGER 模式）后叶子保持影子页0 NX=1，并记录命中
  线程；其它线程/核在暂停期间命中仍走 CC→#BP 排队；
- #NPF 取指分支：DebuggerPaused 且 faultRip==断点地址、当前线程在暂停
  集合中 → 仅放行该线程一次（切干净页 NX=0），x64dbg 自己的 TF 产出
  #DB 投递给 Guest；否则走正常 CC→#BP；
- ReArmByAddress（调试器重写 0xCC）清暂停集合。
效果：同核漏命中窗口从"整个暂停期（秒级）"缩到"原指令单步 + 重写 0xCC
间隔"；其它核始终 NX=1。残余下限：NPT 叶子是 per-CPU 页面视图，单步窗口
内同核其它线程仍可能跑过，属架构下限。

### CC 窗口修复：下一个 VMEXIT 快速收紧
- NP_BP_CPU_STATE 增加 BpCcDirty / BpCcJustArmed；
- NPF 切到 CC 副本时置位；核心新增 NpHvRegisterPostExitCallback 后置回调，
  每次 VMEXIT 分发完成后、返回 Guest 前调用 NpBreakPointPostExit；
- 刚切 CC 的本次退出跳过（防取指重入死循环），下一次 VMEXIT 到来时立即
  重新武装（跳过单步中/暂停中），把 CC 自读窗口从复位周期压到下一次
  VMEXIT；复位线程保留作纯页内循环无 VMEXIT 时的兜底。

产物：output\NpHv.sys（Release）、output\NpHv-Debug.sys（Debug），
Debug/Release 均构建通过。

补充：纯页内循环无 VMEXIT 时的兜底复位周期改为编译期可调
（NPHV_STEALTH_RESET_MS，默认 1ms）；后置回调实际触发快速收紧时输出
节流日志 [bp] cc rearm next-exit cpu=N，便于 VM 内验证。

## 10. 真实附加路径修复（2026-08-28）

问题：开启隐藏调试后 x64dbg 进程列表不完整；随机附加一个进程后 x64dbg 闪退。

## 11. 断点 continue 崩溃与 CRC 0xCC 修复（2026-08-28）

现象：NpBpSelfTest 断点能断下，但 continue 后目标在断点下一页（bp+0x1000）
DEP 崩溃；TEST 程序 CRC 自检直读能查到 0xCC。

根因 1（continue 崩溃）：真实附加 DEBUGGER 分支注入 #BP 前把 VMCB.Rip 推进
到 NRip（断点+1），导致注入异常的 ExceptionAddress=断点+1。TitanEngine 按
真实 INT3 语义（ExceptionAddress=断点）查找断点并恢复 EIP，地址错位后目标
从断点+1 开始执行，错位指令流跑到下一页数据区 → DEP。
修复：注入 #BP 时保持 Rip=断点地址（真实 INT3 的 ExceptionAddress 语义）；
continue 单步取指仍由 #NPF 暂停线程特判放行，不产生无限断点循环。

根因 2（CRC 0xCC）：x64dbg 删除/禁用断点会写回原字节，旧逻辑把它当"非 CC
外部写"转成补丁视图，NPT 断点残留武装，CC 副本继续被直读看到。
修复：新增 NpBreakPointTryDeleteDebuggerBp —— 调试器把断点处写回原字节且
断点不在暂停中时，摘除对应 NPT 断点并拦截本次写（真实页本就没有 CC）。

产物：output\NpHv.sys（Release）、output\NpHv-Debug.sys（Debug），
Debug/Release 均构建通过。剩余边界：进程内直读若发生在"取指切到 CC 副本后、
下一次 VMEXIT 前"，仍可能看到 0xCC（自检 [4] 忙循环场景）。

修正（命中蓝屏）：注入 #BP 时把 RIP 改成断点地址会导致命中即蓝屏，已回退为
注入前推进到 NRip（断点+1），命中链路恢复稳定；continue 的两种取指（断点
地址 / 断点+1）统一由 #NPF 暂停线程特判处理——bp+1 取指回卷到 bp 再执行
原指令，既避免 TitanEngine 不恢复 EIP 时的错位执行，也不改动异常注入语义。

## 12. 0x76 锁页蓝屏修复（2026-08-28）

现象：步进时蓝屏。minidump：BUGCHECK 0x76 PROCESS_HAS_LOCKED_PAGES，
栈为 NpBreakPointSweepThread → NpBreakPointUninstallMonitor →
NpMonFinalRelease → ObDereferenceObject → PspProcessDelete →
MmDeleteProcessAddressSpace。

根因：PEB 影子监视用 MDL 长期 pin 住真实 PEB 页。进程退出通知注册失败
（PsSetCreateProcessNotifyRoutineEx 0xc0000022），只能靠 500ms 清扫线程
回收，但进程删除路径（MmDeleteProcessAddressSpace）先检查到还有锁定页，
直接 0x76。清扫线程的 ObDereferenceObject 成为最后一个引用，触发删除时
锁页尚未释放，必蓝。

修复：PEB 影子监视不再持锁 MDL。
- 安装时 AttachProcess + ProbeForRead 后直接用 MmGetPhysicalAddress 取帧，
  用 MmGetVirtualForPhysical 物理直读填影子页；
- #DB 同步（NpMonSyncPebShadow）改为按 PageGpa 物理直读（MmGetVirtualForPhysical
  任意 IRQL 安全），不再依赖 MDL 系统映射；
- NpMonFinalRelease 移除 MmUnlockPages/IoFreeMdl。
依据：PEB 是私有已提交页，映射存续期间物理帧不会自行迁移，无 MDL 也稳定；
不持锁页后进程退出不再触发 0x76。

产物：output\NpHv.sys（Release）、output\NpHv-Debug.sys（Debug），
Debug/Release 均构建通过。

## 13. 附加瞬间卡死修复（2026-08-28）

现象：选择进程附加的一瞬间 VM 卡死，windbg 都断不进（宿主侧挂起，非普通
bugcheck）。

根因：去掉 MDL 后，PEB 影子安装与 #DB 同步改用 MmGetVirtualForPhysical 物理
直读。该 API 对非系统映射的用户帧可能返回垃圾 VA 而非 NULL，直接 RtlCopyMemory
解引用即系统空间坏引用，SEH 拦不住；安装发生在 DAP 拦截上下文（附加瞬间），
#DB 同步发生在 VMEXIT 上下文，坏引用直接让宿主挂死，windbg 无法捕获。
（NpMemAccess 注释已记录同根因历史蓝屏。）

修复：
- 安装时改用 MmCopyMemory(MM_COPY_MEMORY_PHYSICAL) 做影子快照（PASSIVE 安全，
  无效帧优雅失败）；
- NpMonSyncPebShadow 不再在 #DB VMEXIT 上下文做任何物理读，只重清影子里的
  BeingDebugged / NtGlobalFlag heap 标志；
- 不持锁 MDL 保持（0x76 修复不回归）。
副作用：影子页非调试字段保持安装时快照，调试会话中不再随真实页刷新；PEB
主要字段在进程初始化后基本不变，对隐藏目标影响很小。

产物：output\NpHv.sys（Release）、output\NpHv-Debug.sys（Debug），
Debug/Release 均构建通过。

## 14. 断点 MDL 泄漏修复（2026-08-28）

现象：叉掉目标 EXE 不蓝屏；关闭 x64dbg 时 0x76 PROCESS_HAS_LOCKED_PAGES，
P3=1（一页锁页）。

根因：NpBreakPointInstallEx 在 MmProbeAndLockPages 成功之后，若走
STATUS_NOT_FOUND / STATUS_ALREADY_REGISTERED / STATUS_INSUFFICIENT_RESOURCES
三个提前返回路径，只 detach 就直接 return，没有 MmUnlockPages + IoFreeMdl。
x64dbg 每次 continue/步进重写 0xCC 都会触发一次 InstallEx → ALREADY_REGISTERED
→ 每次泄漏一页无引用锁页；目标进程退出时即 0x76。

修复：新增 ExitPre 统一清理路径，提前返回前解锁并回收 MDL；同时把
bpOccupied/mdlLocked 声明前置，避免 goto 跳过初始化。

产物：output\NpHv.sys（Release）、output\NpHv-Debug.sys（Debug），
Debug/Release 均构建通过。

## 15. 删除断点后仍断下修复（2026-08-28）

现象：x64dbg 删除断点后，目标仍会在该地址断下。

根因：NpBreakPointTryDeleteDebuggerBp 只在断点非暂停时删除；若在断点命中
（DebuggerPaused=TRUE）时删除，原字节写被当成 continue 恢复步忽略，NPT

修复：调试器写回原字节时一律卸载 DEBUGGER 断点。continue 恢复步也会写回
原字节，但其后调试器会重写 0xCC，走 InstallEx 重新安装断点，因此语义不变；

## 16. continue 粘住修复（DeletePending）（2026-08-28）

现象：上一版“删除一律卸载”后，断点命中点击 continue 还会再次断下（粘住）；
多次后 0x76 P3=1。

根因：暂停中写回原字节既可能是 continue 恢复步，也可能是真删除。上一版把
恢复步也直接卸载，若 TitanEngine 顺序是“恢复字节→重写 0xCC→再继续”，新断点
会在取指前重新武装，立即再命中。

修复：改为“待删除”机制：
- 暂停中写回原字节 → 只置 DeletePending，不卸载；
- 重写 0xCC（continue 恢复）→ ReArm 清 DeletePending；
- 非暂停的写回原字节 → 直接卸载（运行中删除）；
- #NPF 命中时若 DeletePending 且不是 continue 暂停线程 → 确认删除：恢复
  真实页、停用断点（Active=FALSE），清扫线程回收；
- 500ms 清扫线程兜底清理残留 DeletePending 断点。

产物：output\NpHv.sys（Release）、output\NpHv-Debug.sys（Debug），
Debug/Release 均构建通过。

## 17. 0x76 根因：补丁视图 MDL 泄漏（2026-08-28）

kb：删除进程的是 ExpWorkerThread（ObpProcessRemoveObjectQueue），不是清扫
线程；!process 确认是 NpBpSelfTest。即我们的进程引用已释放，但目标进程仍带
1 页锁页。

根因：x64dbg 每次 continue 的"恢复原字节"写会进 NpPvApplyWrite → 给断点页
建补丁视图 → IoAllocateMdl + MmProbeAndLockPages pin 住断点页；补丁视图不持
进程引用，且 NpPatchViewValidateAll 声明后从未被调用，视图永不清理。目标
退出时残留锁页 → 0x76 P3=1。

修复：
- WVM 分流：写目标是活动 DEBUGGER 断点页时（continue 恢复步/删除写）不再
  建补丁视图，直接放行真实写（真实页本无 CC，写原字节无害）；
- 新增 NpBreakPointIsDebuggerBpAt 判定。
- 保留 DeletePending 机制（continue 不粘、删除生效）。

遗留：其它页面（非断点页）的补丁视图仍依赖从未被调用的 ValidateAll 清理，
进程退出时同样有 0x76 风险；需把 NpPatchViewValidateAll 节流接入复位线程。

产物：output\NpHv.sys（Release）、output\NpHv-Debug.sys（Debug），
Debug/Release 均构建通过。

## 18. 补丁视图/补丁类功能移除（2026-08-28）

分析结论：游戏 + R0 反作弊场景下，补丁视图（NpPvApplyWrite / NpPatchView*）

  服务注册；
- NpDevIoctl：PATCH_* / VHOOK_* / DATA_PATCH_* IOCTL 返回
  STATUS_NOT_SUPPORTED。

R3（NpHvCtl）：
- CLI 移除 dbg patchlist、vhook、datapatch；
- GUI 页签从 10 个减到 8 个（去掉 VHOOK、数据补丁），移除对应按钮/列表。

## 19. 删除断点仍命中/目标闪退修复（2026-08-28）

现象：清除断点后仍会断下；多运行几次目标进程闪退（无蓝屏）。

根因：暂停中删除断点的“写回原字节”与 continue 恢复步无法靠字节区分。
原 DeletePending 机制在 continue 的 re-CC 重写后清位并重新武装，若 TitanEngine
在删除后仍按恢复步重写 0xCC，断点被重新装回；残留断点再次注入 #BP，而
x64dbg 已删除该断点，目标收到意外断点异常 → 闪退。

修复：改用“恢复写一律卸载 + 重插放行”：
- 写回原字节命中 DEBUGGER 断点 → 一律卸载（运行中删除直接生效）；
- 若卸载时断点在暂停中（可能是 continue 恢复步）→ 记录地址到 reinsert-pass
  集合；
- 后续 0xCC 重装（continue）→ 新断点置 ContinuePass，对当前 continue 取指
  放行一次（防粘住）；
- 真删除没有后续 0xCC 重装 → 断点保持移除，不再注入意外 #BP。

产物：output\NpHv.sys（Release）、output\NpHv-Debug.sys（Debug），
Debug/Release 均构建通过。

## 20. 第二次命中失效/X64DBG 闪退修复（2026-08-28）

现象：第一次命中/继续正常；未取消断点再次触发时断不下，x64dbg 闪退。

日志：每次 continue 的“恢复原字节”写都被 TryDelete 当成删除，断点被
卸载（id=2）→ 继续单步 → re-CC 重装（id=3，带 ContinuePass）→ 第二次命中
→ 再次卸载（id=3）→ x64dbg 在重装前闪退。卸载/重装 churn + ContinuePass
残留干扰了第二次命中。

修复：移除 ContinuePass / reinsert-pass 整套机制，恢复“暂停中恢复写只标记
DeletePending、不卸载”：
- 断点 id 在多次命中/继续间保持不变（无 churn）；
- continue 的 re-CC → ReArm 清 DeletePending，断点保持武装；
- 真删除（无 re-CC）→ DeletePending 由清扫/下次命中确认并停用。

产物：output\NpHv.sys（Release）、output\NpHv-Debug.sys（Debug），
Debug/Release 均构建通过。

## 21. 运行中删除失效/目标闪退修复（2026-08-28）

现象：暂停时取消断点 → 下次不命中（符合删除语义）；运行时取消断点 → 下次
依旧命中，目标闪退；x64dbg 再次附加时“蓝屏”（windbg 实为无 bugcheck 的
用户态断点，宿主卡死嫌疑）。

日志：`#BP hit id=5` 之后没有 `debugger delete` 日志，最终由清扫线程
`uninstall id=5`，说明运行中删除的写没有被 TryDelete 匹配上——断点一直
武装，下次命中注入意外 #BP，目标闪退。

根因：TryDelete 要求写入首字节 == ShadowPage0 首字节，运行中删除时写回
内容可能与安装时快照不一致（或 x64dbg 未写内存），匹配失败。

修复：TryDelete 放宽为“对活动 DEBUGGER 断点地址写任何非 0xCC 字节即视为
删除/恢复”，不再比对影子页首字节；并新增 `[bp] try-delete ...` 诊断日志，
便于确认 x64dbg 是否真的发起了内存写。

产物：output\NpHv.sys（Release）、output\NpHv-Debug.sys（Debug），
Debug/Release 均构建通过。

## 22. 断点地址补丁：保留断点+刷新影子（2026-08-28）

问题：调试器在断点地址改写字节（打补丁）时，非 0xCC 写会被 TryDelete 误判

## 23. 同页多断点：页级共享影子重构（2026-08-28）

问题：NPT 每 4KB 页只有一条叶子，同页第二个断点被 `NpBreakPointIsPageOccupied`

- `BREAKPOINT_INFO` 的影子页、MDL、进程引用、PageGpa 全部改为**非拥有别名**，

  DeletePending）；读路径零改动，只有所有权路径改；
- `NpBpPageRebuildCc`：影子页0 整页拷入影子页1，再按该页全部活动断点偏移打

- `#NPF` 取指改为先查页记录、再按 faultRip 匹配具体断点：HALT → continue

## 24. 进程退出通知 0xc0000022：前提纠偏 + legacy 兜底（2026-08-28）

### 原假设被推翻

此前一直假设「`PsSetCreateProcessNotifyRoutineEx` 返回 0xc0000022 是自隐藏
（`MmVerifyCallbackFunction` 找不到回调所属模块）导致」。查证代码后该前提不成立：

1. `NpConfig.h` 中 `NPTHOOK_SELF_HIDE` **默认为 0**（关闭）。自隐藏版是独立产物
   `output\NpHv-SelfHide.sys`，常规 `NpHv.sys` 不摘链。
2. 时序上 `NpSelfHideInitialize(DriverObject)` 位于 `NptHook.cpp` DriverEntry 的
   **最末尾**，而 `NpBreakPointInitialize`（注册进程通知）作为服务早已初始化完成。
   即便开关打开，注册通知时驱动也还没被隐藏。

因此根因大概率是**驱动映像签名/完整性校验不过**（未签名或绕过 DSE 加载）——
`MmVerifyCallbackFunction` 校验的是映像签名状态，与是否在模块链表里无关。

### 修复：legacy 兜底（已实现，不再依赖排查结论）

`PsSetCreateProcessNotifyRoutine`（legacy 版）**不过 `MmVerifyCallbackFunction`**，
可直接绕开签名限制：

- `NpBreakPointInitialize`：Ex 注册失败 → 退到 legacy；
- 新增 `NpBreakPointProcessNotifyLegacy`（签名 `HANDLE ParentId, HANDLE ProcessId,
  BOOLEAN Create`）；
- 新增 `NpBreakPointUninstallByPidNoRef`：legacy 回调只给 PID、不给 `PEPROCESS`，
  因此拿断点持有的 `OwnerProcess` 反查 PID 做比较（进程退出时
  `PsLookupProcessByProcessId` 可能已失败，不能依赖它）；
- `g_LegacyProcessNotify` 记录实际走了哪条路，Teardown 按同一路移除；
- 500ms 清扫线程保留为最后兜底。

效果：只要 legacy 注册成功，进程退出即摘断点并解锁 MDL，0x76 不再依赖清扫线程
赶得上 `MmDeleteProcessAddressSpace`。

日志新增 `[bp] Ex/legacy process notify ...`、`[bp] process exit pid=N -> removed M bp(s)`。

### ProbeNotify 仍有用，但用法有前提

`ProbeNotify\README.md` 已重写：该驱动**必须用与 NpHv 完全相同的加载方式**，
否则 Phase1 成功只证明「测试签名驱动能注册」，对 NpHv 毫无参考价值。现在它的
定位是「搞清楚根因」，不再阻塞 0x76 修复。

产物：output\NpHv.sys、output\NpHv-Debug.sys，Debug/Release 均构建通过，零警告。

## 25. 进程通知实测结果（2026-08-28，目标机）

`ProbeNotify` 在目标机跑完，结果：

```text
Ex      PsSetCreateProcessNotifyRoutineEx  = 0xc0000022  FAILED
legacy  PsSetCreateProcessNotifyRoutine    = 0x00000000  OK
ctrl    PsSetCreateThreadNotifyRoutine     = 0x00000000  OK
ctrl    PsSetLoadImageNotifyRoutine        = 0x00000000  OK
```

### 纠偏：不是"驱动未签名"

第 24 节推测根因是「驱动映像签名/完整性校验不过」。**对照组把这条推翻了**：
`PsSetCreateThreadNotifyRoutine` 与 `PsSetLoadImageNotifyRoutine` 同样调用
`MmVerifyCallbackFunction`，两者都返回 0x00000000 —— 基础映像校验是通过的。

正确解释：`PsSetCreateProcessNotifyRoutineEx` 在基础校验之外还有一道**更高的
认证级别门槛**（测试签名 / 自签名 / 绕过 DSE 加载的驱动过基础校验，但过不了
这道）。legacy 版没有这道门槛，因此直接成功。

### 结论

第 24 节落地的 legacy 兜底**在本机确认可行**，0xc0000022 不再是阻塞项。
进程退出即摘断点、解锁 MDL，不再需要 500ms 清扫线程去抢
`MmDeleteProcessAddressSpace` 之前的时间窗。

### 复测 NpHv 时应看到的日志

```text
[bp] Ex process notify failed 0xc0000022 -> legacy fallback
[bp] legacy process notify registered (no image verification path)
[bp] process exit pid=N -> removed M bp(s)
```

最后一行出现，说明进程退出时断点与其页级 MDL 已被即时回收。

### NPT hook 掉 Ex 的签名验证段？不做

评估结论：**收益为零**。Ex 与 legacy 在内核里走同一个 `PspSetCreateProcessNotifyRoutine`，
同一个注册数组、同一个通知分发点（时机完全一致，都在 `PspExitProcess` 路径上——
所有线程已终止、进程对象尚未进 `PspProcessDelete`）。patch 验证段只是让注册
通过，通知仍走同一条路；Ex 比 legacy 多给的只有 `PPS_CREATE_NOTIFY_INFO`
（CommandLine / 镜像名 / ParentPid），摘断点用不到。而代价是实打实的：内核
patch 要随版本维护偏移、KVA Shadow/重定位，还给反作弊多一个"内核代码被改"的
检测面。不做。

### 25.2 回调触发实测（ProbeNotify 第二轮，2026-08-28）

### 25.1 补充修复：legacy 回调补齐监视清理（2026-08-28）

## 26. 断点删除闭环：overlay 真实附加锚点修复（2026-08-29 实机验证通过）

### 问题现象（用户逐轮复现，日志逐条坐实）
x64dbg **运行期**删除断点后，再运行目标函数仍被断下。断点列表有、执行流
照过、NPT 影子页切换一切正常，但断点永远删不掉；且删除动作在驱动侧
**完全不可见**（无 0x48 写、无 0xCC 写、无对断点地址的读）。

### 根因链（三层，逐层挖出）
1. **无痕断点"读写不对称"**：写 0xCC 被 WVM 拦截转成 NPT 断点（真实内存
   永不落 CC）；读同一地址若返回真实字节 0x48，调试器会认为"断点没了"，
   删除时不再写回原字节 → 驱动侧 try-delete 永远等不到信号 → 断点残留。
2. **overlay 判据错误（真正的病根）**：呈现 0xCC 的读视图
   （`NpBreakPointOverlayCcForRead`）判据用的是
   `NpPseudoDbgFindByDebugger(callerPid,...)` —— **真实附加（passthrough）
   模式下 pseudo 会话不存在，恒返回 FALSE** → overlay **从未生效**。
   铁证：整份日志 rvm 行无数条，无一条带 `-cc` 标记。
   后果：TitanEngine `DeleteBPX` 删除断点时**先读内存验证**，读到 0x48
   （非 0xCC）就认为断点已不在、**不写回 orgdata** → 驱动收不到任何信号。
3. **zombie reap 的 target=0 盲区**：真实附加下 `NtDebugContinue` 的 Arg1
   是调试对象句柄而非进程句柄，target 解析恒 0 → 清扫被提前 return 跳过
   （已修，作为兜底）。

### 修复（2026-08-29 05:28 产物，Debug/Release 零警告）
| 项 | 内容 |
| --- | --- |
| `NpDebugHideIsDebuggerOf(DebuggerPid, VictimPid)` | 查 DAP 拦截时 `NpDebugHideNoteDebugger` 写入的 `g_ProtectedPids`/`g_ProtectedDebuggerPid` 锚点表（真实附加模式可用） |
| overlay 判据 | `NpPseudoDbgFindByDebugger` → `NpDebugHideIsDebuggerOf(callerPid, pid)` |
| overlay 返回 BOOLEAN | 是否覆盖了活动断点地址 → RVM 诊断对"涉及断点地址的读"**无条件打印**（`[dbghide] rvm-cc` 标记，节流 512 但关键路径不节流） |
| `NpBreakPointDeleteByCcWrite` | 非暂停期收到 0xCC 写且断点已存在 = 删除（防 x64dbg `BpEnable` 重读 oldbytes 被污染成 0xCC 的路径） |
| `NpBreakPointReapZombieOnContinue` | target=0 语义改为"不过滤进程、扫描全部 DEBUGGER 断点"，且移到 target==0 提前 return 之前（兜底层） |

### 实机验证（2026-08-29 05:3x，用户确认）
**运行期删除断点成功、再运行不再断下。** 删除闭环：
```
x64dbg 删除 → DeleteBPX 读验证 → 0xCC（overlay 生效）→ 写回 orgdata(0x48)
→ 驱动 try-delete 收到 → 摘除 NPT 断点
```

### 删除判定现有三层（按优先级）
1. 写回原字节（≠0xCC）→ `NpBreakPointTryDeleteDebuggerBp`；
2. 非暂停期写 0xCC → `NpBreakPointDeleteByCcWrite`（oldbytes 污染路径）；
3. 命中后 continue 无 step-over 动作 → `NpBreakPointReapZombieOnContinue`
   （兜底，实测日志 `[bp] zombie reaped id=4` 确认已触发过）。

### 复盘教训（重要）
- **同源 bug 三处**：pseudo 会话查询（`NpPseudoDbgFindByDebugger`）在真实
  附加模式下恒 FALSE，同时坑了 continue 的 target 解析、overlay 判据两处。
  排查真实附加路径时，涉及"当前调试器是谁"的查询一律用 DAP 锚点表。
- **关键证据路径不能节流**：RVM 诊断曾统一节流 64，把"调试器读断点地址"
  的证据吞掉，导致"x64dbg 没读"的错误结论。涉及断点地址的读一律无条件打印。
- **验证"结果"而非"动作"**：`[bp] verify ... cc=0xCC`、`rvm-cc b=CC` 这类
  断言式日志（验证 0xCC 是否真的呈现/在页里）是定位此类问题的决定性工具。
