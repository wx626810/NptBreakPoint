## LSTAR 与 NpHook 关系（今日结论）
- `NpHookInstallHook` = NPT 克隆页钩子（4K 物理页影子 + 0xCC + #NPF/#BP 状态机），
  与 LSTAR（MSR 劫持按 syscall 号分流）是两套独立机制
- LSTAR 启用时 `NpDebugHideSetEnabled` 直接置标志返回，不装任何 NpHook
  （QIP/RVM/WVM/DAP/SCT 全由 NpLstarSyscallDispatch 分流）→ 本机零冲突
- 非 LSTAR 回退路径保留（不注释掉）：LSTAR 不可用的机器（KPTI/初始化失败）
  仍需 NpHook 兜底，注释掉 = 那类机器 debug hide 全废
- 同页互斥对 LSTAR 机器无影响；对非 LSTAR 机器仅在 QSI/QIP 撞页时
  降级跳过 QIP 钩子（有日志），WVM/RVM/DAP/SCT 不受影响

## 已知限制（按决策记录，不改代码）

### NPT 恒等映射固定 512GB — 消费级定位下的已知边界
- `NpConfig.h: NPTHOOK_NPT_MAP_GB = 512`，NPT 只建 0~512GB 的恒等映射；
  `MmGetPhysicalMemoryRanges` 仅用于总量统计，不参与映射尺寸决策。
- 影响：物理地址 ≥ 512GB 的内存页不在 NPT 内 → guest 触碰即 `#NPF(Present=0)`
  → 驱动注入 #PF → guest 内核收到指向合法内存的页错误 → 蓝屏/数据损坏。
- 现有防线（不改代码，记录现状）：`NpHv.cpp` 初始化时 `MmGetPhysicalMemoryRanges`
  累加总容量，`totalBytes > 512GB` 则 `STATUS_HV_INSUFFICIENT_BUFFERS` 拒绝虚拟化。
  注意该判据的漏洞：稀疏区间（如 256GB@0 + 256GB@1TB）总量可 ≤512GB 但
  最高物理地址越界 — 正确判据应为 max(BaseAddress+NumberOfBytes)。
- 决策：主要客户为消费级 CPU（AM5 平台上限 192GB，距 512GB 余量 2.6 倍），
  不做动态建表。触发时表现为 sc start 返回失败（拒绝启动），非蓝屏，可接受。
- 商业版若需支持 HEDT/EPYC：两方案 —
  a) 加载时按最高 PFN 决定 PML4 填充项数（最小改动）；
  b) 升 4 级映射覆盖 512TB（每核 +2MB 常驻页表，一劳永逸）。
