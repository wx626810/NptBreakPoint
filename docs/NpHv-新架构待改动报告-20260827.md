# NpHv 新架构待改动报告（伪附加 + 虚拟内联钩子）

- 日期：2026-08-27
- 状态：**已实施（2026-08-27 全量落地）**
- 目标：无痕（含目标自读）+ 0 窗口 + 跨版本，三者结构性同时成立
- 本报告只列"要改什么、怎么改、接口是什么"，不含实现细节推演

---

## 1. 背景与目标

当前框架 = 方案B 克隆重定位（NpReloc + 克隆页执行）。该方案解决了 0x50（相对寻址），但存在结构性残留：

| 读路径 | 方案B 现状 | 新架构目标 |
|---|---|---|
| R0 物理直读 | 原页（干净）✓ | ✓ 保持 |
| 其他进程共享页（CoW） | 原页 ✓ | ✓ 保持 |
| 用户态 AC 读（syscall） | 不可区分 | LSTAR 按调用者分流 |
| **R0 attach 读** | **克隆页（补丁可见）✗** | **无补丁字节 → 原页 ✓** |
| **目标自读/自校验** | **克隆页（补丁可见）✗** | **无补丁字节 → 原页 ✓** |

**核心判据**：只要内存里存在"补丁字节"，自读与 attach 读就必然读到它（AMD NPT 无 execute-only 位，取指/数据读共用一条路径）。因此新架构的第一原则是：

> **补丁不再写入任何被校验的字节；行为修改全部发生在执行层（虚拟内联钩子）与系统调用层（LSTAR 伪附加）。**

新架构由三块拼成：

1. **LSTAR 接管 + 伪附加**（调试子系统层面，替代真实 DebugObject/DebugPort）；
2. **虚拟内联钩子**（内存补丁层面，字节零修改）；
3. **数据补丁**（数据读层面，读点虚拟化 / 纯数据页影子）。

## 2. 新架构总览

### 2.1 系统调用拦截（LSTAR）

```
用户态 syscall（任意进程）
   → LSTAR = 驱动池跳板（Guest ring0，非 hypervisor）
   → 比对 syscall 号 ∈ 拦截表？
       否 → jmp 原始 KiSystemCall64（零 hypervisor 退出，零开销）
       是 → vmmcall 进 hypervisor
            ├─ 伪附加类：NtDebugActiveProcess / NtRemoveProcessDebug /
            │            NtWaitForDebugEvent / NtDebugContinue / NtQueryInformationProcess
            ├─ 读写分流类：NtReadVirtualMemory / NtWriteVirtualMemory
            └─ 上下文类：NtSetContextThread / NtGetContextThread
            → 伪造或转发，sysexit 回用户态
```

- **性能关键**：未列入拦截表的 syscall 在跳板内直接 jmp 回原始入口，**不产生 VMEXIT**；
- **无递归**：内核内部 Zw* 直调不走 LSTAR（这正是"内核态直调拦不了"的原因），伪附加因此依赖"数据干净"而非调用拦截；
- RDMSR隐身（新增）：
- RDMSR 0xC0000082 同样进 VMEXIT hypervisor回真KiSystemCall64 反作弊rdmsr看到永远干净
- 别名：找nt .text段内CC slack（对齐空洞）GPA_cave -> HPA池（跳板） NPT叶读影0(CC) 执行影1(跳板) LSTAR= GPA_cave 值本身落在nt范围内 过范围校验
跨版本只依赖 syscall 号

### 2.2 伪附加流程

```
x64dbg: DebugActiveProcess(pid)
  → NtDebugActiveProcess 被 LSTAR 拦
  → hypervisor：校验目标、登记 {伪句柄=会话ID, 目标Pid, 调试器Pid, 事件队列}
  → 返回伪句柄（一个数字；不创建 DEBUG_OBJECT，不写 EPROCESS.DebugPort）
  → EPROCESS 全程零痕迹（R0 直读干净）

x64dbg: WaitForDebugEvent
  → NtWaitForDebugEvent 整个 syscall 被拦（真实内核实现不执行）
  → 回调在调试器线程上下文查伪会话表（伪句柄永不进 Ob 句柄表，
     ObReference 路径不存在 → 不会 INVALID_HANDLE）
  → KeWaitForSingleObject(自建 KEVENT, Timeout) 阻塞该线程
  → 事件就绪（见下）→ ProbeForWrite 写 DEBUG_EVENT 到用户 buffer
  → 返回 STATUS_SUCCESS（事件内 hThread/hProcess 为真实句柄，
     在调试器进程上下文 ZwOpenThread/ZwOpenProcess 创建）

x64dbg: DebugContinue → 确认事件 → 解锁冻结线程 / 重新武装断点
x64dbg: DebugActiveProcessStop → NtRemoveProcessDebug → 注销伪会话，恢复
```

**事件队列（自建，不依赖 DEBUG_OBJECT）**：

```
NPT #BP 命中（VMEXIT）→ 冻结命中线程
  → 入队 NpPseudoDbg 事件队列（链表 + KEVENT）→ KeSetEvent
调试器 Wait 回调被唤醒 → 写 DEBUG_EVENT → 返回
```

- 事件来源：附加快照（PEB.Ldr 模块 / 线程枚举）+ 运行期（NPT #BP、TF #DB、PsSetLoadImageNotifyRoutine 模块加载、PsSetCreateThreadNotifyRoutine 线程创建）；
- 断点命中不再"注入 #BP 给 Guest 调试体系"（目标无调试端口，注入会崩），改为：冻结命中线程 + 事件入队 + 唤醒调试器 Wait；
- 线程冻结：命中线程用现有 HALT 机制；全线程冻结为 v1 增强项（见 §5 边界）；
- **附带收益**：伪句柄不在任何句柄表 → R0 句柄表扫描也扫不到调试会话（比真实附加更干净）。

### 2.3 虚拟内联钩子（内存补丁）

```
目标函数 HookPoint VA（原函数入口/补丁点）
  → 超管页内 TF 单步（NX 陷阱页优化：仅入口钩时一次 #NPF）
  → #DB 退出时 RIP == HookPoint → 改 guest RIP = CaveVA
  → Cave（hypervisor 拥有的可执行页）执行：
      补丁逻辑（用户提供/生成）+ 剩余块（NpReloc 重定位，position-independent）
  → Cave 末尾 jmp 回原函数后续指令原地址
原函数字节全程未改 → 自读/自哈希/attach 读/物理扫描全部读到原始字节
```

- 复用：NpReloc（剩余块重定位）、NpDisasm（Hook 点定位/边界）、NpBreakPoint（TF/页级控制）；
- Cave 是目标进程地址空间里的一块新可执行内存（VAD 可见）——这是本方案唯一残留面（见 §5）。

### 2.4 数据补丁

- **读点虚拟化（主）**：不碰数据字节，把"读取该数据的指令"用虚拟钩子改语义（如 `if rax==&flag → rax=补丁值`）；
- **纯数据页影子（备）**：NPT not-present → 每次访问 #NPF → 翻转 leaf 到影子页单步执行该指令再翻回；仅适合低频数据页。

### 3.4 拦截表（LSTAR 初始清单）

> **关键语义**：以下每个 syscall 都是**整个调用被拦截**（真实内核实现不执行），
> 因此伪句柄只存在于伪会话表、永不进 Ob 句柄表；"等待 Dispatcher Object"的
> 语义由回调里的 KeWaitForSingleObject(自建 KEVENT) 提供；事件队列由本驱动
> 自建。这是"调试协议完整语义重实现"，不是简单返回假值。

| syscall | 动作 |
|---|---|
| NtDebugActiveProcess | 伪会话登记，返回伪句柄（会话 ID），不建 DebugObject/不写 DebugPort |
| NtRemoveProcessDebug | 注销伪会话，恢复（分离） |
| NtWaitForDebugEvent | 伪会话表查句柄 → KeWait 自建 KEVENT → 写 DEBUG_EVENT 到用户 buffer（含 DebugEventSize 栈参数处理，Win10 20H1± 差异）→ 返回 |
| NtDebugContinue | 确认事件，解锁冻结线程 / 重武装断点 |
| NtQueryInformationProcess | 分流：调试器→"已附加"假值；AC/目标→干净值（7/0x1E/0x1F 及 DebugPort 查询） |
| NtSuspendThread / NtResumeThread | 调试器对事件 hThread 操作 → 转发为线程冻结/恢复 |
| NtGetContextThread / NtSetContextThread | 调试器读/改线程上下文：DR 读写→NPT 转发 + 假 DR 回显（drprobe 已有基础），目标侧 DR 保持干净 |
| NtReadVirtualMemory | 分流：调试器→真值/补丁视图；AC→原值 |
| NtWriteVirtualMemory | 分流：调试器 0xCC→NPT 断点、补丁→虚拟钩子；AC 写→放行 |

**事件内句柄真实性**：EXCEPTION_DEBUG_EVENT.hThread / CREATE_PROCESS_DEBUG_EVENT.hProcess
必须是真实句柄（x64dbg 会对它们 GetThreadContext/SuspendThread）。在 Wait 回调
（调试器进程上下文）用 ZwOpenThread/ZwOpenProcess 创建后填入事件。

**x64dbg 兼容性核对项（P2 真机确认）**：附加成功后 x64dbg 对 QIP 的
ProcessDebugPort/ProcessDebugObjectHandle 具体查询序列、WaitForDebugEventEx
的 DebugEventSize 传参、事件句柄的使用方式。

> RtlLookupFunctionEntry 非 syscall，不在 LSTAR 拦截范围；虚拟钩子无克隆栈帧，展开保持原生正确，无需处理。

## 5. 已知边界与残留面（如实声明）

1. **Cave 页 VAD 可见**：虚拟钩子的代码洞是目标进程新分配的可执行页，枚举 VAD/已提交内存的 AC 能看到"多了一块"。缓解：优先复用nt/目标模块 .text内CC slack作Cave（GPA_cave别名 无新VAD）；无slack时再NtAllocateVirtualMemory + VAD 不被哈希段 接受低危痕迹。
2. **行为级校验**：AC 调用函数验证返回结果（而非哈希字节）时无法伪造——永恒的军备竞赛面。
3. **全线程冻结**：v1 冻结命中线程；全线程冻结（x64dbg 式"全部暂停"）为增强项。
4. **x64dbg QIP 兼容细节**：x64dbg 附加后查询哪些调试类信息（ProcessDebugPort 等）需在 P2 用真机核对，按观察调整假值（P3 预留）。
5. **LSTAR 跳板健壮性**：跳板需严格保序（r10=用户 rsp、rcx=返回 RIP、r11=FLAGS）、处理中断/嵌套、KiSystemCall64 不同版本入口差异——P1 专门验证。
6. **数据页影子仅限低频**：not-present 翻转按访问计费，热数据页不可用（读点虚拟化是主路径）。
7. **物理直读 EPROCESS**：伪附加使 DebugPort/DebugObjectHandle 根本不存在（数据干净），无需伪造——与既有结论一致。
8. **伪附加 = 调试协议完整重实现（P2 范围显著大于"3 个 syscall 拦截"）**：需覆盖 DAP/Remove/Wait/Continue/QIP/Suspend/Resume/GetSetContext/RVM/WVM 全部语义（含阻塞、超时、DebugEventSize、事件内真实句柄、暂停-继续协议），缺一个 x64dbg 即卡死；这是本架构最主要的成本与风险点。
9. **异常事件投递范围**：v1 只投递断点（#BP/0x80000003）与单步（#DB/0x80000004）及模块/线程生命周期事件；目标自身的访问违例等第一次机会异常投递为增强项（需 NPT #PF 捕获或 KiDispatchException 联动，P2 后评估）。
10. **伪句柄不进句柄表**：这是收益不是残留——R0 句柄表扫描扫不到调试会话；但意味着任何"按句柄反查对象"的调试器自检路径也会失败（x64dbg 不使用，无需处理）。

### 8.9 根因修复：LSTAR 从未真正生效（2026-08-27 第六版）

带 `sc DAP=214 ...` 的日志证实 syscall 号解析正确、跳板已构建，但 DAP/QSI
全部不命中。根因是 AMD SVM 的 **`vmload` 语义**：

- `SvLaunchVm` 每次 `vmrun` 前执行 `vmload rax`，VMLOAD 会把 VMCB
  StateSaveArea 中的 `STAR/LSTAR/CSTAR/SFMASK/SYSENTER_*` 重新加载进 MSR
  （AMD APM Vol.2 15.5.2）；
- 原实现在 MSR 拦截回调里 `__writemsr` 物理 MSR，下一轮 vmload 立即覆盖回
  原值 → Guest 永远执行原始 KiSystemCall64，跳板从未生效；
- 修复：WRMSR 0xC0000082 改为把新值写入**每 CPU VMCB.StateSaveArea.LStar**
  （当前 CPU 下一次 vmload 生效，其它 CPU 同样更新），不再写物理 MSR
  （顺带消除 host 侧 LSTAR 被改的隐患）；
- 跳板分配从 `MmAllocateContiguousMemory` 改为
  `ExAllocatePool2(POOL_FLAG_NON_PAGED_EXECUTE)`，保证 NX pool opt-in
  下跳板页可执行（否则首次 syscall 即 NX #PF）。

预期：本次修复后 DAP/QIP/QSI 才会真正进入跳板分发器，伪附加与
prochide QSI 过滤同时生效。

### 8.10 R3 蓝屏修复：跳板布局与返回栈（2026-08-27 第七版）

LSTAR 真正生效后“打开 R3 即蓝屏”，跳板首次实跑暴露三个此前被
vmload 覆盖掩盖的 bug：

1. **布局重叠**：`hit` 被算成 `nSc*11`（比对链结束处），miss 跳转写在
   那里后又被 hit 代码覆盖。非拦截 syscall 会掉进 hit 路径 → 全系统
   syscall 错乱。已改为 `hit = chainBytes + 14`（miss 跳转 + 原地址槽之后），
   并加运行时自检（miss 跳转字节必须完好）。
2. **返回栈错误**：sysretq 前 `mov rsp, r10`，但 syscall 入口 r10 保存的是
   第一参数，不是用户栈（用户栈存在 `gs:[10h]`）。首次真拦截返回时
   RSP=参数值 → 用户进程/系统崩溃。已把 `KPCR.UserRsp` 存进帧
   `[rsp+0x48]`，返回前恢复。
3. **rdi 未恢复**：跳板用 rdi 临时传 syscall 号但从不恢复，破坏非易失
   寄存器约定。已删除该临时用法（VMMCALL 处理不依赖 rdi）。

至此跳板可安全实跑；请重新加载 `output\NpHv.sys` 后按“先开 NpHvCtl 等
刷新 → 新开 self → x64dbg 附加”复测。

### 8.12 虚拟机整机卡死：活跃 VMCB 被跨核改写（2026-08-27 第九版）

新现象不是蓝屏而是**整机卡死**（windbg 无 bugcheck）。根因：此前 WRMSR
回调里直接遍历所有 CPU 写 `VMCB.StateSaveArea.LStar`，但**正在运行 Guest
的 CPU，其 VMCB 处于硬件使用中，不允许被其它核改写**——被改写的核
VMRUN 状态异常后陷入 VMEXIT 循环，整机表现为冻结。

修复：
- MSR 回调只改【当前 CPU】自己的 VMCB.LStar；
- 新增 `VMMCALL_LSTAR_SET` + `AsmVmmCallLstarSet`：驱动在 PASSIVE
  上下文按 CPU 亲和性逐个执行 vmmcall，让每个核在自己的 VMEXIT 上下文
  应用新 LSTAR（与 NpBreakPoint 的 DR 拦截同款模式）；
- LSTAR 激活延后到首次 Refresh（NpHvCtl IOCTL）：驱动加载阶段完全不动
  LSTAR，消除启动期风险；
- `NpLstarHandleVmmcall` 增加 CPL==0 校验，防止用户态 vmmcall 篡改 LSTAR。

请重新加载复测：加载不应再卡死；打开 NpHvCtl 触发刷新时日志出现
`[lstar] refreshed trampoline ... (N intercepts)` 且系统继续正常运行。

### 8.13 卡死定位：VMEXIT 上下文禁用 DbgPrint（2026-08-27 第十版）

里程碑日志定位到：`sync done` 之后、首个 `vmmcall SYSCALL` 出现之前卡死，
且 KD 无法 break（所有核 GIF=0 卡在 host）。

根因：调试用 `NpDebugPrint`（DbgPrint）被放进了 VMEXIT 处理器。DbgPrint
走 KD 传输，若调试器侧状态不对会阻塞；CPU 在 GIF=0 的 host 上下文里卡在
DbgPrint 内 → 该核死锁，KD 永远 break 不进，与“Debuggee is running but
cannot break”完全吻合。

修复：VMEXIT 处理器内全部改用非阻塞环形日志 `NpHvLogPrint`
（NpBreakPoint 既有同款用法）；DbgPrint 只保留在 PASSIVE 的刷新/同步路径。

若复测仍卡死（最后一行仍是 `sync done` 且无 `vmmcall SYSCALL`），下一步
检查跳板页可执行性/NPT 映射，或改用不依赖 KD 的观察通道。

### 8.14 同步窗口竞态：跳板就绪门闩（2026-08-27 第十一版）

去掉 VMEXIT DbgPrint 后，卡死点前移到 `sync cpu=2`。分析：同步期间
CPU0/1 已换上新 LSTAR，第一个被拦截的 syscall 可能落在正在被同步线程
钉住的 CPU 上（或与亲和性切换交互），形成死锁。

修复：跳板命中路径入口增加**就绪门闩** `g_LstarReady`：
- `LSTAR` 写与全核同步完成前，门闩为 0 → 命中路径直接 `jmp` 回 miss
  （原样转发 KiSystemCall64），不进入分发器；
- 全核 `sync done` 后置 1（`KeMemoryBarrier`）才放行；
- 已用 objdump 复核门闩编码（`cmp byte ptr [rip+disp],0 / jne +5 /
  jmp miss`）与跳板整体指令流。

这消除了“首个被拦 syscall 撞上同步窗口”的竞态；若此后仍在 `sync done`
之后卡死，则说明是首命中分发器自身问题，下一步加 VMEXIT 风暴看门狗
（同退出码连续超阈值即 KeBugCheck 出转储）来拿现场。

### 8.15 架构定型：LSTAR 虚拟化时按核预置 + 固定槽位表（2026-08-27 第十二版）

同步窗口竞态修掉后仍随机卡在 `sync cpu=N`，说明“运行时逐核改 LSTAR”
这条路本身不可靠。最终定型为**不再运行时改 LSTAR**：

- `NpLstarPreInitialize`（虚拟化前）构建 16 固定槽位跳板：每个槽
  `cmp eax, [rip+slot] / je hit`，槽位值来自全局表（空槽 = 0xFFFFFFFF
  永不匹配），miss 直通原入口；
- `NpArchSvmVirtualizeProcessor` 在每个核自己的上下文中把
  `VMCB.StateSaveArea.LStar` 预置为跳板地址（VMRUN/vmload 生效），
  去虚拟化时各核恢复原 LSTAR；
- 刷新（NpHvCtl IOCTL）只写全局槽位表 + 就绪门闩，**零 MSR 写、零跨核
  同步**，彻底消除该卡死类别；
- 跳板仍保留就绪门闩、帧保存、vmmcall 分发、sysretq(0F 07) 返回，
  指令流已逐条 objdump 复核。

复测预期：加载即带跳板（槽位空闲全直通，无 VMEXIT）；打开 NpHvCtl 后
日志出现 `refreshed slots: N intercepts armed`，不再有 sync 过程；此后
x64dbg 附加走伪附加。

### 8.16 KPTI：LSTAR 跳板页在 syscall 入口不可达（2026-08-27 第十三版）

槽位定型后，连 R3 都没开、仅加载就卡死：LSTAR 在虚拟化时已预置为跳板，
说明**跳板页本身在 syscall 入口取指即故障**。根因是目标机启用 KPTI
（内核页表隔离）：syscall 入口时 CR3 仍是用户页表，非分页池跳板页未映射，
第一条指令取指即 #PF/挂死。此前各版本 LSTAR 从未真正生效，因此未暴露。

修复：
- `NpLstarPreInitialize` 从真实 KiSystemCall64(Shadow) 序言解析
  `cmp gs:[disp32],0`，并读该 KPCR 字段判定 KPTI 是否 ACTIVE；
- KPTI ACTIVE 时：不预置 LSTAR、`NpLstarIsEnabled=FALSE`，驱动安全加载，
  调试隐藏/prochide 回退旧 NpHook 路径（无冻结，但受目标机克隆能力限制）；
- KPTI off 时：维持槽位跳板 + 按核预置 LSTAR 的新架构。

复测：加载后日志应出现 `[lstar] pre-init: KPTI ACTIVE (LSTAR path disabled)`
或 `KPTI off`，据此确认走哪条路径。

### 8.17 真根因：RIP 相对 disp32 溢出到远全局（2026-08-27 第十四版）

KPTI 判定为 off 后仍卡死，且卡点提前到“IOCTL device created”（首个被
虚拟化核的第一次 syscall）。真正的根因：

- 固定槽位跳板用 `cmp eax, [rip+disp32]` 引用驱动 `.data` 里的
  `g_TrampSlots` / `g_LstarReady`；
- 非分页池跳板页（如 `FFFF8201...`）与驱动镜像 `.data`（如 `FFFF8047...`）
  的内核 VA 差可超过 ±2GB，`disp32` 符号扩展溢出 → 第一条比较指令就
  读到错误地址 → #PF → CPU 挂死；
- 修复：**槽位表（16×4B）与就绪标志放进跳板页自身**（offset 0x800 /
  0x840），RIP 相对引用永远在同页内；刷新/门闩写入改经页内指针；
- KPTI 探测保留（本机为 off）。

至此，LSTAR 入口链路的已知故障类别（vmload 覆盖、跨核 VMCB、同步竞态、
disp32 溢出）全部排除。

### 8.18 回归报告设计：LSTAR 落在 nt .text CC slack（2026-08-27 第十五版）

多次复测表明：跳板放非分页池页时，syscall 入口在该机行为不可靠
（首取指即冻结、无 VMEXIT、KD 无法 break、看门狗不触发）。根因判断：
偏离了报告 §2.1 的硬性要求——“LSTAR 别名应落在 nt .text 的 CC slack 内，
值本身落在 nt 范围内”，即跳板必须与原 syscall 入口同页（该页被用户 CR3
保证映射）。

实现：
- `BuildTrampolineTo(OutBuf, BaseVa)`：按目标基址生成；槽位表/就绪标志回到
  驱动 `.data`，跳板内用 `push r8 / movabs r8, slot / cmp eax,[r8] / pop r8`
  绝对寻址（避开 disp32 溢出，也不在 nt .text 写数据区）；
- `FindCcSlack` 在原 LSTAR 所在 4KB 页找连续 CC（≥0x220），命中则用 MDL
  写入跳板字节并预置 LSTAR 到该地址；无 slack 回退可执行池（并打印）；
- 卸载时还原 slack 原 CC 字节；
- 自检修正：`cmp eax,[r8]` 必须带 REX.B（`41 3B 00`），此前缺前缀会被
  解码成 `[rax]`，已修正并经 objdump 复核。

复测：加载日志应出现
`trampoline in nt .text CC slack at ...`（成功）或
`no CC slack, fallback pool trampoline`（需扩大 slack 扫描策略）。

### 8.19 SMAP：syscall 入口用户栈被 ring0 触碰（2026-08-27 第十六版）

exec-pool 探针证明 EXECUTE 池可执行后，冻结头号嫌疑转为 **SMAP**：
跳板在 syscall 入口（仍是用户栈、AC 未置位）执行 `push r8`，Windows 默认
启用 SMAP → ring0 写用户栈即 #PF → 首取指后立即挂死，无 VMEXIT、
KD 无法 break，与全部现象吻合。

修复：跳板布局改为“**先切内核栈**”：
- 入口先执行标准序言（swapgs / 保存用户栈到 gs:[10h] / 切内核栈）；
- 整个比对链、门闩、帧都在内核栈上执行（push/pop 不再触碰用户栈）；
- miss 路径用 `mov rsp, gs:[10h]` 还原用户栈 + swapgs 后原样进入
  KiSystemCall64；
- 槽位改为基址+偏移（movabs r8, slots + cmp eax,[r8+off]），代码缩到
  ~0x180，提高入口页 CC slack 命中率；
- 已用 objdump 复核新布局。

复测：若不再冻结 → SMAP 是根因；若仍冻结且日志为 `no CC slack`，
则入口页确实无空洞，LSTAR 路径在该机不可行，转回 NpHook 或换环境。

### 8.20 跳板字节序回归：`je` 被写成 `84 0F`（2026-08-27 第十七版）

复测时首取指即冻结（无 VMEXIT、KD 无法 break、看门狗不触发），
全量反汇编跳板后定位到字节发射器回归：

- `Emit16(&p, 0x0F84)` 按小端写出为 `84 0F`，解码成
  `test %cl,(%rdi); sahf; ...`，第一条 `cmp` 之后立即进入垃圾指令流，
  在 syscall 入口处直接 #PF/挂死，与全部现象吻合；
- 修复：`je` 改为显式 `Emit8(0x0F); Emit8(0x84)`；`jmp [rip+0]`
  同样改为显式字节，删除已无用的 `Emit16`；
- 新增跳板自检：`out[chainStart+12]==0x0F && +13==0x84`，再错会返回
  `STATUS_UNSUCCESSFUL` 而不是带病安装；
- 构建日志同时修正（此前 chain/miss 重复打印同一个偏移）；
- `NtWaitForDebugEventEx` 加入基础拦截表（原仅分发器有分支，槽位表
  从未包含该 syscall 号，属隐藏功能缺口）。

复测预期：加载日志出现 `trampoline: 14 slots ... (slots idle)`，
`IOCTL device created` 之后继续输出 `All processors virtualized (4)`，
不再冻结。

### 8.21 VMEXIT 现场读取与剩余 DbgPrint 修正（2026-08-27 第十八版）

全量走查 LSTAR 命中链路时又发现两个会导致“刷新后首个命中即冻结”

至此 LSTAR 加载与命中两条链路（跳板字节、栈切换、VMCB 现场、

### 8.22 SYSRET 返回模式修正：`0F 07` → `48 0F 07`（2026-08-27 第十九版）

- 当前跳板已改为 `48 0F 07`，并更新源码注释，避免再次踩坑。

至此 hit 返回路径的 CS/SS 目标模式与 RCX/R11/RSP 恢复全部对齐。

### 8.26 安全拷贝首次调用 0x50：禁止在跳板里懒解析 API

### 8.27 真根因：跳板漏 `stac`，SMAP 下 AC=0 导致所有用户访问 0x50
（2026-08-27 第二十四版）

对宿主 26100 `ntoskrnl.exe` 的 `KiSystemCall64` 逐字节核对后发现：

```asm
; 真实 KiSystemCall64（26100）
swapgs
mov  gs:[10h], rsp
mov  rsp, gs:[1A8h]
... 建 KTRAP_FRAME ...
stac                       ; 服务分发前打开 AC（SMAP 放行用户页）
... KiSystemServiceStart ...
... 退出：sysretq 用 R11 恢复用户 RFLAGS（AC 自动归 0）
```

之前所有 0x50 的共同根因是：跳板 hit 路径复制了 `swapgs` 序言、
补了 `sti`，但**从未执行 `stac`**。目标机 SMAP 开启时，内核在 AC=0
状态下直接访问用户页（读第 5 参数、读 PEB、写事件缓冲）全部被硬件
拒绝，`ProbeForRead/__try` 拦不住（内存管理器直接 0x50）。这也是
旧 NpHook 路径正常而 LSTAR 路径崩的原因：旧回调跑在真实 syscall
服务分发之后，AC 已是 1。

修复（跳板 hit 路径）：
- `vmmcall` 后先 `sti` 再 `stac`（0F 01 CB），再调用分发器；
- 返回序列在 `cli` 前补 `clac`（0F 01 CA），随后
  `swapgs / mov rsp,r10 / sysretq`（sysretq 本身用 R11 恢复用户
  RFLAGS，AC 必归 0）；
- 布局复核：`sti=0x124 stac=0x125 clac=0x150 len=0x15d`。

至此 LSTAR 分发上下文与真实 syscall 的 IF/AC 语义对齐；安全拷贝改造
继续保留作为双保险。

复测预期：首个 QIP 命中可直接访问用户缓冲，不再 0x50；后续
WaitForDebugEvent / RVM / QSI 过滤路径同理。

### 8.28 RVM 转发 0x50：SSDT 定位命中伪表，入口落到不可执行区
（2026-08-27 第二十五版）

AC 语义对齐后仍蓝屏，但这次是**取指**失败：

- minidump：`0x50`，`AV.Type=Execute`，故障地址
  `nt+0x9e954`（位于 nt 头部/.rdata 区域，不可执行），
  上一帧返回地址 `NpHv+0x77d1` = `LstarHandleReadVirtualMemory`；
- 根因：26100 的 `NtReadVirtualMemory/ZwReadVirtualMemory` 不在导出表，
  `NpSyscallResolveRoutine` 走 SSDT 兜底；旧扫描逻辑
  “QIP/QSI 锚点首命中 + 64 项 RVA∈[0x1000,SizeOfImage)” 在 26100 上
  命中了 .rdata 里的伪表，`KiServiceTable[63]` 被读成 RVA 0x9e954，
  `mb + soff` 落在不可执行区 → CFG 间接调用即取指 0x50；
- 旧逻辑还会在真实 KiServiceTable 内部任意 4B 对齐处命中锚点
  （表是连续 RVA 长段，移位后条目也能偶然对齐 QIP/QSI），
  首次命中不等于表起点。

修复（NpSyscall）：
- 新增 `SGetExecutableRange`：从 PE 段表读可执行段范围；
- 4B 表扫描改为“锚点命中 + 连续代码 RVA 段长评分”，选**最长段**
  （真实 KiServiceTable 数百项必赢；段起点自然获得最长分）；
- 4B 解析强制要求 `mb != 0`，禁止 `tb + soff` 兜底；
- `NpSyscallResolveRoutine` 增加兜底校验：SSDT 解析出的地址必须落在
  可执行段内，否则返回 null（宁可功能降级，不调用坏地址）；
- 双锚点地址增加“必须在 nt 映像内”校验，防止 24H2 导出哨兵值污染。

复测预期：RVM/WVM/QIP 转发地址正确，不再跳进 nt 数据区；
若某函数仍解析失败，日志/行为降级为 STATUS_NOT_IMPLEMENTED，
不会蓝屏。

### 8.29 R3 GUI 不弹出：只武装可处理 syscall + 分发诊断日志
（2026-08-27 第二十六版）

驱动已稳定不蓝屏，但打开 R3 GUI 没有窗口。最可能原因：GUI 进程启动期
的 QIP/RVM/QSI 等调用被 LSTAR 拦截，转发指针解析失败或转发路径卡住，

本次加固：
- `NpLstarRefresh` 只把“能真正处理”的 syscall 写入槽位表：
  DAP/Remove/Wait/WaitEx/Continue 全程自处理，必然武装；
  QIP/QSI/RVM/WVM/GCT/SCT/Suspend/Resume 要求对应 g_Orig* 转发指针
  解析成功才武装，失败则放行给原始 KiSystemCall64，不再把正常进程
  的调用变成 STATUS_NOT_IMPLEMENTED；
- `ResolveSyscalls` 打印每个 g_Orig* 的实际地址（或 NULL），
  一次运行即可确认 26100 SSDT 解析是否全部成功；
- `NpLstarSyscallDispatch` 打印前 64 次命中的
  `sc/pid/序号`，未处理分支单独打印，便于定位 GUI 卡住的 syscall。

复测：加载驱动后先看日志中的 `[lstar] orig ...` 与

### 8.32 仍卡：全镜像扫描兜底仍慢，改为 LSTAR 服务描述符快速定位
（2026-08-27 第二十九版）

缓存/锚点优化后点击 dbghide 仍卡：目标机为嵌套虚拟化，即使只扫一次
整份 ntoskrnl 也慢到 GUI 线程在 DeviceIoControl 里长阻塞。

对宿主 26100 `KiSystemCall64` 服务分发反汇编发现根本不需要扫描：

```asm
lea  r10, [rip+disp]        ; KSERVICE_TABLE_DESCRIPTOR
...
mov  r10, [r10]             ; TableBase = KiServiceTable
cmp  eax, [r10+rdi+0x10]    ; NumberOfServices
movsxd r11, [r10+rax*4]     ; 4B 表项
```

实现：`SFindServiceTableByLstar` 扫描 `KiSystemCall64` 前 0x1000 字节里的
`lea rX,[rip+disp32]`，把目标当服务描述符读 `TableBase`，用
`TableBase + QIP_SC*4 == QIP地址` 校准；命中即得到 KiServiceTable，
零全镜像扫描。该函数作为 `NpSyscallFindServiceTable` 的**首选快速路径**，
原有全镜像扫描降级为兜底。

复测预期：点击“调试隐藏开启”立即返回；驱动日志出现
`[syscall] service table via LSTAR fast path = 0x... (4B=1)`，
随后 `[lstar] orig ...` 与 `refreshed slots: N intercepts armed`。

### 8.34 卡点确认与根治：解析整体前置到驱动加载期

### 8.35 快速路径失配：24H2 QIP 导出是 Zw 包装地址
（2026-08-27 第三十二版）

`lstar-scan` 日志显示找到了多个 `lea` 目标（含 0x12018C0 等描述符），
但没有任何一个满足 `TableBase + QIP_SC*4 == QIP地址`：

```text
lstar-scan: ki=... known=FFFFF80689BAB830 sc=25
lstar-scan: off=0x394 target=FFFFF8068A4018C0
...（无 fast path）→ 掉进全镜像扫描 → 卡死
```

根因：Windows 11 24H2 的 `NtQueryInformationProcess` 导出在运行时
指向的是 **Zw 包装/syscall stub**，不是 SSDT 表里真正的 Nt 处理函数
地址；用它做锚点校准 KiServiceTable 永远失败。

修复：`SFindServiceTableByLstar` 不再只靠 QIP 锚点，增加**描述符结构
校验兜底**：
- 读 `KSERVICE_TABLE_DESCRIPTOR[+0x10]` 的服务数（100~2000）；
- 对 `TableBase` 做连续代码 RVA 段长测量（正向，不要求段起点）；
- 前 64 项低 12 位必须多样（≥4），排除 `.rdata` 里的页对齐伪表
  （0x200000/0x200001 这类规律值）；
- 选最长代码段作为 KiServiceTable（4B 表）。

复测预期：加载日志出现 `service table via LSTAR fast path = ... (4B=1)`，
不再掉进全镜像扫描。

### 8.36 防卡死收尾：删除全镜像扫描兜底 + 解析边界

- `lstar-scan` 增加 `text=...`、`no table (lea=N)` 日志，快速路径失败时

### 8.37 Win11 SSDT 表项编码：RVA<<4，必须 sar 4 解码
（2026-08-27 第三十四版）

windbg 直接读目标机 `KeServiceDescriptorTable` 后确认：

```text
TableBase        = fffff805d0eda4d0
NumberOfServices = 0x1e9
表项示例         = 08d13601 / 03647104 / ...
```

这些值不是明文 RVA：Windows 10/11 的 KiServiceTable 表项是
`(RVA << 4) | flags`，内核分发时用 `sar r11,4` 再 `add r10,r11`。
此前驱动按明文 RVA 判断，导致 `run=0`、结构校验失败、快速路径失配，
最后退到导出表拿到 Zw 包装地址，转发时把 svchost 打崩
（0xc0000305 / Access Violation）。

另修正：`SizeOfImage` 在 PE32+ OptionalHeader 的偏移是 `+0x38`，
不是 `+0x50`（`+0x50` 是 SizeOfStackCommit），`SValidateImage` 与
快速路径回退边界都改对。

修复：
- 表项解码统一为 `entry >> 4`（有符号算术移位，兼容负向 RVA）；
- 段长测量、低位多样性、地址计算全部基于解码后 RVA；
- 真实地址 = ntBase + (entry >> 4)。

复测预期：加载日志出现 `service table via LSTAR fast path = ... (4B=1)`，
`orig QIP=...` 等为 SSDT 真实处理函数地址；svchost 不再异常。

### 8.38 表项偏移基准：TableBase + (entry>>4)，不是镜像基址
（2026-08-27 第三十五版）

快速路径命中后出现新崩溃：

```text
service table via LSTAR fast path = FFFFF803C44DA4D0 (4B=1)
dispatch sc=25 ...
Access violation: nt!PiControlGetSetDeviceStatus+0x1b
```

原因：Win10/11 的 4B 表项解码后是**相对 TableBase 的偏移**，内核用
`TableBase + (entry >> 4)`。此前按“镜像基址 + RVA”计算，把 QIP 解析成
了 `PiControlGetSetDeviceStatus`（恰好位于错误公式得到的地址），
转发即崩。

修复：`NpSyscallGetRoutineByNumber` 4B 路径改为
`addr = TableBase + (entry >> 4)`；`mb` 不再参与计算。
验证：`TableBase(nt+0xDA4D0) + 0x8D1360 = nt+0xDAB830`，与导出表返回的
真实 NtQueryInformationProcess 一致。

复测预期：`orig QIP` 等地址正确，QIP 转发不再落到无关函数，
`PiControlGetSetDeviceStatus` 崩溃消失。

### 8.39 sysretq 回错地址：跳板帧与分发器 shadow space 重叠
（2026-08-27 第三十六版）

SSDT 地址正确后，svchost 仍崩溃，`.cxr` 给出决定性证据：

```text
rip=ffffffffc0000001  rcx=ffffffffc0000001
rsp=0000009e61dfdd68  r10=0000009e61dfdd68  r11=0000000000000246
```

`r10/r11/rsp` 都恢复正确，只有 `rcx` 变成了分发器返回值
`0xC0000001`（STATUS_UNSUCCESSFUL）→ `sysretq` 用它当了用户 RIP。

根因：跳板帧把用户 RIP 存在 `[rsp+0x10]`，而 `call NpLstarSyscallDispatch`
时 x64 约定主调方要为被调函数预留 `[rsp..rsp+0x18]` 的 shadow space；
分发器（或其内层调用）写该区域时覆盖了 `[rsp+0x10]/[rsp+0x18]`
（保存的 RCX/R11）。

修复：
- 跳板帧整体上移 0x20：`sub rsp,0x70`，保存区改到
  `[rsp+0x20..0x58]`，`[rsp+0x00..0x18]` 留给 shadow space；
- 用户 RIP/RFLAGS/arg1-4/syscall#/用户栈 分别存
  `+0x20/+0x28/+0x30/+0x38/+0x40/+0x48/+0x50/+0x58`；
- vmmcall 时 syscall# 读取偏移同步改为 `guestRsp+0x50`；
- 恢复序列读取 `+0x58/+0x28/+0x20`，`add rsp,0x70` 后 clac/cli/swapgs/
  sysretq。

复测预期：QIP 命中后正常返回用户态，不再出现 `RIP=0xC0000001`。

### 8.40 非受保护 syscall 透传：重新进入原始 KiSystemCall64
（2026-08-27 第三十七版）

shadow space 修复后不再蓝屏/回错地址，但 Explorer 打开文件夹变卡、
svchost 崩溃，日志出现：

```text
WER/CrashAPI: ERROR NtQueryInformationProcess failed
WER/CrashAPI: ERROR Failed to read the peb from the process
Access Violation in svchost
```

根因：被拦截的 QIP/RVM/WVM 对**非受保护进程**也走分发器，并直接调用
真实 Nt* 函数；从自定义跳板帧调用真实 syscall 处理函数会破坏调用
上下文（PreviousMode/栈帧等），导致真实 QIP 失败、PEB 读不到。

修复（结构性）：
- 分发器对“不处理”的调用置位 `Frame->Reserved = 'SLTP'` 透传标记；
- 跳板检测到标记后：恢复 EAX/RCX/R11/R10/RDX/R8/R9/用户 RSP，
  `clac/cli/swapgs` 后 **jmp 回原始 KiSystemCall64**，由真实内核
  重新执行该 syscall（正常建陷阱帧、正常 PreviousMode）；
- 受保护目标仍由分发器伪造/处理（QIP 假值、RVM 物理读等）；
- 基础拦截表全部武装，不再依赖 g_Orig* 转发指针。

复测预期：打开文件夹、svchost 正常运行；只有受保护/伪会话目标走
分发器，其余 syscall 透明透传。

### 8.41 伪附加 Wait 定位：DebugObjectHandle → 按调试器 PID 回退

### 8.42 CPU 窗口空白：DEBUG_EVENT 写超 + 同步事件只留一个信号
（2026-08-27 第三十九版）

x64dbg 能附加（DAP/会话/快照均成功），但 CPU 窗口无代码、下不了断点。
两个事件层 bug：

1. **DEBUG_EVENT 写超**：`NPHV_DEBUG_EVENT` 是 0xB8 字节，真实 x64
   `DEBUG_EVENT` 是 0xA8 字节；Wait 把 0xB8 字节写进用户 0xA8 缓冲，
   溢出 16 字节污染 x64dbg 栈 → 状态损坏。修复：写入长度上限 0xA8。
2. **同步事件只留一个信号**：会话 Event 是 SynchronizationEvent
   （自动复位），快照一次入队 CREATE_PROCESS + 多个 LOAD_DLL 时，
   多次 KeSetEvent 只留下一个信号；调试器只拿到第一个事件，第二次
   Wait 永久阻塞。修复：取走一个事件后若队列仍有剩余，再次
   `KeSetEvent`。

另加 `[pseudo] wait ...` / `wait event code=...` 日志，便于下一轮直接
确认事件流。

复测预期：x64dbg 依次收到 CREATE_PROCESS、LOAD_DLL，CPU 窗口显示
目标代码，可下断点。
