# NptBreakPoint — AMD NPT 无痕断点 / 反反调试研究框架

> 基于 NptHook（AMD NPT 无痕 Hook 框架）扩展的断点/监视子系统。
> 核心能力：把调试器的软件断点（INT3）**藏进 NPT 影子页**——真实内存永不落 0xCC，
> 反作弊扫不到断点；x64dbg 仍能正常下断点、命中、单步、删除。

---

## 1. 项目定位与架构

```
demo / 测试驱动（NpBpSelfTest / ProbeNotify）
   ↓
services（业务服务：断点、监视、调试隐藏、伪附加、进程隐藏）
   ↓
core（hypervisor 核心：VMEXIT 分发、NPT 页表、影子页、事件注入）
   ↓
platform（NpHv.sys 驱动框架）
```

- **双影子页方案**（AMD 无 execute-only 位）：影子页0 = 干净副本 + NX（读视图）；
  影子页1 = 入口处打 0xCC 的执行副本。NPT 叶子按需在两者间切换。
- **LSTAR syscall 拦截**：NtReadVirtualMemory / NtWriteVirtualMemory /
  NtQueryInformationProcess / NtDebugActiveProcess 等 12 个 syscall 经 vmmcall
  分发到服务层。
- **每 4KB 页一条 NPT 叶子**：断点/监视按页共享，页记录持有双影子页与 MDL。

## 2. 技术重点

### 2.1 同页多断点：页级共享影子（2026-08-28 重构）
- 问题：NPT 每页只有一条叶子，同页第二个断点被 `IsPageOccupied` 拒绝 →
  x64dbg 步过在同页下临时断点会**静默失效**。
- 方案：新增 `BREAKPOINT_PAGE` 页记录（双影子页 / MDL / 进程引用 / RefCount /
  页内断点链）；`BREAKPOINT_INFO` 改为**非拥有别名**（读路径零改动，只动所有权）。
- `NpBpPageRebuildCc`：影子页0 整页拷入影子页1，再按该页**全部**活动断点偏移打
  0xCC；#NPF 取指先按 GPA 查页、再按 faultRip 匹配具体断点。
- **验证状态**：实机确认 0x1818 + 0x1824 同页共存、各自独立命中。

### 2.2 #BP 的 RIP 语义歧义（AMD 专属，2026-08-29 APM 核实）
- APM Vol2 §8.2.4：`#BP is a trap-type exception. The saved instruction
  pointer points to the byte after the INT3.` → VMCB.Rip 可能是 **INT3+1**。
- 但 §15.7.1 又为 INT3 提供 nRIP（= INT3 之后）—— 两份表述指向不同结论。
- **方案**：先按 rip 匹配，失败再试 `rip-1`；命中日志标注实际语义。实机确认
  本机为 `(rip=addr)`。

### 2.3 无痕断点必须"读写对称"（overlay）
- 写 0xCC 被 WVM 拦截转成 NPT 断点（真实页不留痕）；**读同一地址若返回真值，
  调试器会认为断点没了** → 删除时不再写回原字节 → 断点残留。
- `NpBreakPointOverlayCcForRead`：仅对**已附加的调试器**把断点地址呈现为
  0xCC，内存扫描/反作弊/目标自身仍读真值 —— 无痕性与调试器可用性的平衡点。
- 判据必须用**真实附加锚点**（DAP 拦截时登记的 `g_ProtectedDebuggerPid`），
  不能用 pseudo 会话查询（真实附加模式下恒 FALSE，见踩坑 #7）。

### 2.4 断点删除判定三层
1. 写回原字节（≠0xCC）→ `NpBreakPointTryDeleteDebuggerBp`；
2. 非暂停期写 0xCC → `NpBreakPointDeleteByCcWrite`（oldbytes 污染路径）；
3. 命中后 continue 无 step-over → `NpBreakPointReapZombieOnContinue`（兜底）。

### 2.5 进程退出通知：legacy 兜底
- `PsSetCreateProcessNotifyRoutineEx` 在未签名/绕过 DSE 的驱动上恒返回
  0xc0000022（额外签名认证门槛，Thread/Image 对照组实证）。
- legacy `PsSetCreateProcessNotifyRoutine` 不过这道门槛 → 兜底注册，进程退出
  即摘断点+解锁 MDL，0x76 时间窗关闭。回调只给 PID → 按 `PsGetProcessId`
  反查匹配。

### 2.6 物理内存访问：一律 MmCopyMemory
- `MmGetVirtualForPhysical` 对失效帧**不返回 NULL**，竞态下返回垃圾 VA →
  读 PML4E 全 0 → 页表遍历 100% 失败（`walk fail stage=pml4-np`）。
- 已踩两次（PEB 影子安装、页表遍历读），全部改用
  `MmCopyMemory(MM_COPY_MEMORY_PHYSICAL)`。

### 2.7 跨核 ICache 失效
- AMD 跨核修改代码：硬件不保证 I-cache 一致性（整页拷贝不满足"单 store
  对齐 8 字节"约束）→ `NpBpInvalidateShadowCaches`（KeInvalidateRangeAllCaches）。
- 刻意不放进 `NpBpPageRebuildCc`（后者在自旋锁内调用，持锁发 IPI 有死锁风险）。

## 3. 踩坑与过坑方法（按时间线）

| # | 坑（现象） | 根因 | 过坑方法 |
|---|-----------|------|---------|
| 1 | MSBuild 被 WorkBuddy 沙箱按 LOLBin 拦截 | 沙箱策略 | `python run_build.py <Debug/Release> Build`（subprocess 包装） |
| 2 | 断点下了、执行流过了、却永远断不下，日志无痕 | **0xCC 从未打进影子页**：`NpBpPageRebuildCc` 只对 `bp->Active` 打 CC，而 `Active=TRUE` 在 RebuildCc **之后** 3 行才置位（重构回归） | 装完即验：`[bp] verify id=N off=0x%03X clean=0x%02X cc=0x%02X` —— **验证"结果"而非"动作"**，一条断言日志直接指认 |
| 3 | 命中后 NRip 为 0 → Guest RIP 写成 0 跳飞 | CPU 不支持 NRIPS / 未填充 | `NRip==0` 回退 `bp->Address + 1` |
| 4 | 项目笔记「AMD 拦截 #BP 时 Rip=INT3 地址，经 AMD 文档核实正确」—— 实际是错的 | 错误记录没有文档依据，误导多轮排查 | 按图索骥查 APM §8.2.4 得相反结论 → 代码兼容两种语义 + 日志标注；**笔记里的"核实正确"必须能指向具体章节** |
| 5 | 运行期删除断点后仍被断下 | ①无痕读写不对称（写被拦、读返回真值）②TitanEngine `DeleteBPX` 删除时**先读内存验证**：读到 0x48 就认为断点已不在、不写回原字节 → 驱动收不到信号 | overlay 只对调试器呈现 0xCC；判据用真实附加锚点 |
| 6 | overlay 从未生效（日志 rvm 无一条 -cc） | 判据用 `NpPseudoDbgFindByDebugger`，**真实附加模式下 pseudo 会话不存在，恒 FALSE**（与 continue 的 target=0 同一病根） | `NpDebugHideIsDebuggerOf` 查 DAP 锚点表（`g_ProtectedPids`↔`g_ProtectedDebuggerPid`） |
| 7 | zombie reap 不触发 | `NtDebugContinue` 的 Arg1 是调试对象句柄而非进程句柄 → target 恒 0 → 函数开头 `if(TargetPid==0) return` 直接跳过 | target=0 语义改为"不过滤进程"；reap 调用挪到 target==0 提前 return 之前 |
| 8 | 单步走时 CPU 窗口代码"一闪一闪" | **step-over churn**：单步的恢复步写回原字节（置 DeletePending）→ #NPF 删除确认段抢跑误删 → uninstall→install 循环 → 断点页在存在/消失间抖动 | #NPF 确认段加 `!bp->StepOverSeen` 门槛；ReArm 清 StepOverSeen；reap 判据 `DebuggerPaused && (DeletePending || !StepOverSeen)` |
| 9 | 物理直读 100% 失败，全部退化 attached fallback | `NpReadPhysicalQword` 用 `MmGetVirtualForPhysical`，对失效帧返回垃圾 VA → PML4E 读成全 0 | 统一 `MmCopyMemory(MM_COPY_MEMORY_PHYSICAL)`；判据：`walk fail` + fallback 能读到正确数据 → 一定是读取方式问题 |
| 10 | bash heredoc 写含 Windows 路径的补丁脚本，路径变成 `////` | `\\\\` 转义层数失控 | 改用 Edit 工具直接改文件；改完做 **UTF-16 字节级校验**（hexdump） |
| 11 | ProbeNotify 驱动"没输出" | `DbgPrintEx` 走 IHVDRIVER 组件，Win10/11 默认掩码 0 全被抑制；且无落盘通道 → "没输出"和"没跑"分不清 | 纯 `DbgPrint`（无组件过滤）+ 落盘线程（`\SystemRoot\xxx.log`）+ R3 活体事件；返回码当布尔通道 |
| 12 | 进程通知 Ex 注册 0xc0000022，误判"驱动未签名" | **没带对照组**：Thread/Image 通知同样过 `MmVerifyCallbackFunction` 且都成功 → 基础校验是过的，Ex 有额外签名认证门槛 | 排查驱动必须带对照组；实测判定后再下结论 |
| 13 | 关键证据被日志节流吞掉 | RVM 诊断统一节流 64，把"调试器读断点地址"的证据藏了 → 得出"x64dbg 没读"的错误结论 | **涉及断点地址的读无条件打印**（rvm-cc 标记）；关键证据路径绝不节流 |
| 14 | 同源 bug 坑两处 | pseudo 会话查询在真实附加下恒 FALSE，同时坑了 target 解析和 overlay 判据 | 真实附加模式下，涉及"当前调试器是谁"的查询一律用 DAP 锚点表 |

# 2026-09-03 补充踩坑

## 27. DISPATCH_LEVEL 严禁 RtlStringCbVPrintfA/vsnprintf（两次 0xA 蓝屏）
- `wctomb_s → RtlpIsUtf8Process` 读 PEB+0x34C；PEB 分页，IRQL=2 不能等页 → 0xA
- VMMCALL 处理器全程 DISPATCH（KeRaiseIrqlToDpcLevel + GIF=0），
  任何 `%s`/宽字符格式化日志都会踩
- 修复：NpHvLogPrint 开头 `if(KeGetCurrentIrql() >= DISPATCH_LEVEL) return;`
- 判据：dump 里 `PROCESS_NAME=NpHvCtl.exe` + 栈 `vsnprintf→wctomb_s→RtlpIsUtf8Process`
  + Arg2=2 + Arg1=PEB附近用户地址 → 就是这个

## 28. NpHvCtl.exe 内嵌驱动 ≠ output\NpHv.sys（"新EXE旧驱动"陷阱）
- EXE 从 `embedded_drivers.h:g_NpHvBytes[]`（XOR 0x5A^(i&0xFF)）解密落盘加载，
  **不读** `output\NpHv.sys`
- 只重编驱动不重嵌 → 用户装到的永远是旧字节；"我确定是新EXE" 也救不了
- 固化流程：**改驱动 → run_build.py → 重嵌 embedded_drivers.h → build_ctl.bat**，
  三步缺一不可；验证判据：`Select-String embedded_drivers.h '_len ='` 与
  `output\NpHv.sys` 大小一致

## 29. Hook 同页互斥 → STATUS_ALREADY_REGISTERED → R3 err=183
- NPT 克隆页钩子按 4K 物理页互斥（NpHookFindHookByPage）；
  selfhide/prochide 的 QSI 钩子与 debug-hide 的 QIP 钩子在 ntoskrnl 同页
- LSTAR 启用时 NpDebugHideSetEnabled 走标志位路径不装 NpHook → 无冲突；
  仅非 LSTAR 回退路径会撞
- 修复：SetEnabled 容忍 ALREADY_REGISTERED 降级跳过；NpDevDebugProtect 幂等化
- 彻底解法（待做）：Hook 移植 BREAKPOINT_PAGE 同页多钩子共享影子

## 30. hypercall 早退必须复制 device 路径的后续动作
- GUI/CLI 加 hypercall 快路径时，device 路径尾部的联动
  （prochide 开关、DoWndHide 窗口改名/恢复）不会自动执行
- 新增传输层时，把"传输"与"业务后置动作"分离，早退分支也要跑完业务

## 31. NPT 固定 512GB 恒等映射的边界（已知限制，消费级定位不改码）
- `NPTHOOK_NPT_MAP_GB=512` 写死，`MmGetPhysicalMemoryRanges` 不参与映射构建。
- >512GB 物理地址的页不在 NPT → `#NPF(Present=0)` → 注入 #PF → guest 内核
  把合法内存当页错误 → 蓝屏。
- 现有防线：init 时 totalBytes 超限即 `STATUS_HV_INSUFFICIENT_BUFFERS` 拒绝虚拟化
  （失败而非蓝屏）。判据漏洞：应比对最高物理地址（含稀疏区间场景），非总容量；
  且 `NpDebugPrint` 已空化，该拒绝是无声的 — 排障时直接看 sc start 的错误码。
- 决策记录（2026-09-03）：消费级客户（AM5 上限 192GB）不触界，不改动；
  HEDT/EPYC 支持留给商业版（按最高 PFN 建表 或 4 级映射 512TB）。
